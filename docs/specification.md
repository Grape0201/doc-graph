**ナレッジグラフ型ドキュメント管理システム**

要件定義・仕様書（OSS選定 兼 システム構成案）

作成日: 2026年7月20日 / バージョン: 0.1（ドラフト）

# 1\. 概要

本書は、PDF文書・OCRテキスト・付随する詳細メタデータを管理し、日本語での全文検索、および文書間参照関係を中心としたグラフ可視化を実現するシステムの要件と、採用OSS・全体構成をまとめたものである。

従来型の「検索ボックス＋一覧表示」のドキュメント管理ではなく、グラフ探索を主UIとし、文書・キーワード・機器番号などを結ぶナレッジグラフとして情報を提示することを特徴とする。

# 2\. 背景・目的

- 大量のPDF文書（数テラバイト規模）とOCRテキスト、複雑なメタデータ（1文書あたり約30項目）を一元管理したい。
- メタデータには文書管理IDと、他文書を参照する「関連文書管理ID」が含まれ、文書同士がネットワーク構造を持つ。
- キーワードや機器番号など、文書以外の要素も含めた関連性を可視化し、探索的に情報へアクセスできるようにしたい。

# 3\. スコープ

## 3.1 対象データ

- PDFファイル本体（総容量：数テラバイト規模）
- PDFのOCRテキスト（全文検索対象）
- メタデータ（1文書1レコード、約30項目。文書管理ID・関連文書管理ID・キーワード・機器番号を含む）

## 3.2 対象外（現時点）

- OCR処理自体（OCR済みテキストが存在する前提。OCRエンジン選定は別途）
- 認証基盤の構築（必須要件ではなく、将来対応の可能性がある程度）
- 監査ログ機能
- 外部システムへの再配布・ソフトウェアとしての頒布

# 4\. 全体アーキテクチャ

検索エンジンとグラフDBの役割を分離し、それぞれの得意領域を活かす2ストア構成とする。

|     |     |     |
| --- | --- | --- |
| **コンポーネント** | **採用OSS** | **役割** |
| 全文検索・メタデータ検索 | OpenSearch（kuromojiプラグイン） | OCRテキストの日本語全文検索、30項目メタデータの複合条件検索・絞り込み |
| グラフストア | Neo4j（Community Edition） | 文書－文書（参照関係）、文書－キーワード、文書－機器番号など多種ノード間の関係管理・探索クエリ |
| バックエンドAPI | 自前実装（言語未定） | 検索APIとグラフ展開APIを統合し、フロントへ提供 |
| フロントエンド | 自前実装＋グラフ描画ライブラリ（Cytoscape.js/Sigma.js等） | 検索窓、グラフ可視化、ノードクリック時のメタデータ・PDFリンク表示 |
| PDFファイル本体 | ファイルサーバー／オブジェクトストレージ | PDF実体の保管。OpenSearch・Neo4jにはパス／IDのみ保持 |

データフロー概要：PDF・OCRテキスト・メタデータを取り込み時に分岐させ、OpenSearchには検索用インデックスとして、Neo4jにはノード・エッジとして登録する。フロントエンドは検索APIとグラフAPIの両方を呼び出し、1画面上で検索結果とグラフ探索を連携させる。

# 5\. 機能要件

## 5.1 グラフ可視化UI（メイン画面）

- 検索窓にキーワードを入力すると、該当するノード（文書・キーワード・機器番号等）がグラフ上に表示される。
- 表示するノードを起点として、関連ノードを何階層（何ホップ）まで展開表示するかをユーザーが選択できる。
- ノードをクリックすると、当該ノードの詳細（文書メタデータ、PDFファイルへのリンク等）が表示される。
- ノードは種別ごとに視覚的に区別できる（文書／キーワード／機器番号／その他）。

## 5.2 全文検索

- OCRテキストに対する日本語全文検索。形態素解析（kuromoji等）による高精度な検索。
- 検索結果は最終的にグラフ上のノードとして表示される。

## 5.3 メタデータ検索・絞り込み

- 約30項目のメタデータに対する複合条件検索（AND/OR、範囲指定等）。
- 文書管理ID・関連文書管理IDを用いた参照関係の特定。

## 5.4 ノード・エッジ管理

- ノード種別：文書（Document）、キーワード（Keyword）、機器番号（Equipment）。将来的に種別追加の余地を持たせる。
- エッジ種別（例）：文書→文書（参照）、文書→キーワード、文書→機器番号。
- 大量関連（ハブ化）が発生するノードについて、表示件数上限や除外設定を検討する。

# 7\. データモデル概要（ドラフト）

## 7.1 OpenSearch インデックス（例）

- doc_id（文書管理ID）、related_doc_ids（関連文書管理ID、配列）
- ocr_text（OCRテキスト、kuromoji解析対象）
- メタデータ項目 × 約30（キーワード、機器番号、その他分類項目）
- pdf_path（PDFファイルへの参照パス）

## 7.2 Neo4j グラフスキーマ（例）

- (:Document {doc_id, title, ...}) -\[:REFERENCES\]-> (:Document)
- (:Document) -\[:HAS_KEYWORD\]-> (:Keyword {name})
- (:Document) -\[:USES_EQUIPMENT\]-> (:Equipment {equipment_no})
- Neo4j側は探索用の最小プロパティ（ID・表示名程度）に留め、詳細メタデータはOpenSearch／別DBへの問い合わせで取得する方式を基本とする（Neo4j肥大化の回避）。

# 8\. 未決事項・追加確認が必要な項目

以下は今後の詳細設計に向けて確認・決定が必要な事項。

- 参照関係（関連文書管理ID）は双方向として扱うか、一方向（参照元→参照先のみ）として扱うか。
- グラフ展開のホップ数上限、および1回の展開で表示するノード数の上限設計。
- グラフ可視化の主用途：「1文書を起点にネットワークを見る」が中心か、「全体マップを俯瞰する」用途も必要か（後者は数万ノード規模の描画性能設計が必要）。
- キーワード・機器番号ノードの生成方法：メタデータからの機械的抽出か、人手によるタグ付けが必要か。
- ハブ化しやすいノード（共通キーワード等）に対する表示制御（除外設定、表示件数上限など）の要否。
- OpenSearchとNeo4jを同一サーバーに同居させるか、分離するか。
- メタデータのマスタとなるデータソース（別システムのDBを読み取り専用で参照するか、自前で保持するか）。
- 検索窓での検索対象範囲：OCRテキストのみか、ノード名（キーワード・機器番号）も対象に含めるか。
- バックエンド・フロントエンドの実装言語／フレームワークの選定。
